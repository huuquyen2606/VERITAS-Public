# Adversarial Malware Integrity and Functionality Evaluator

This repository contains scripts and utilities designed to evaluate the functionality and integrity of adversarial malware samples against their original baseline behavior. It provides metrics to measure the preservation of semantic behavior after adversarial transformations, using both API call sequence alignment and symbolic execution-based system call alignment.

## Overview

The evaluation suite includes four primary scripts, each targeting a specific layer of functionality or integrity checking:

- **`mab_technique_functionality_check.py`**: Checks if adversarial features (signatures) generated by the MAB technique have disrupted the expected signature sets of the original samples. Measures functional similarity using Jaccard Similarity.
- **`dqeaf_technique_integrity_check.py`**: Checks for simple live integrity for the DQEAF technique by ensuring that an adversarial sample still executes and generates an observable API trace.
- **`dqeaf_technique_functionality_check.py`**: Uses `angr` to perform Control Flow Graph (CFG) static structure integrity checks.
- **`malguise_technique_functionality_check.py`**: A specialized, optimized evaluator for MalGuise API sequences. It calculates the Normalized Edit Distance between original and adversarial API traces to accurately report Semantics Preservation Rates.
- **`veritas_technique_intergrity_functionality_checks.py`**: The most robust evaluation engine. It performs a tiered check:
  - **Layer 1 (Integrity Gatekeeper)**: Ensures the sample executes and generates traces.
  - **Layer 2 (BinSim Triton/Z3)**: Performs a deep semantic check on critical system calls, using symbolic execution and constraint solving to identify equivalent behaviors despite structural transformations.
  - **Layer 3 (Fast Smith-Waterman API)**: Fallback evaluation using a C-optimized Smith-Waterman alignment on API call sequences if Layer 2 is bypassed or unavailable.

## Requirements

The codebase expects a Linux environment (tested on Ubuntu) due to the use of a pre-compiled C-extension (`fast_sw.so`). 

### Python Dependencies

Ensure you have Python 3.8+ installed. Install the required Python packages by running:

```bash
pip install -r requirements.txt
```

The `requirements.txt` includes:
- `numpy`
- `tqdm` (for dynamic progress bars)
- `editdistance` (C-compiled fast Levenshtein implementation)
- `triton-library` (for Binary Analysis / SMT lifting)
- `z3-solver` (for constraint solving)
- `angr` (for static analysis)

### C-Extension (`fast_sw.so`)

The `fast_sw.so` is a compiled shared object for fast sequence alignment. It is provided in this bundle. No additional compilation is necessary as long as you are on a compatible Linux machine. If you face import errors regarding `fast_sw`, you will need to recompile the extension from its original C source on your machine.

## Dataset Structure

For the scripts to function, the dataset must be structured accurately. All scripts expect the `.npz` dataset files to be located relative to the script's execution path.

You must place your data into the following directory tree:

```
integrity_functionaltiy_evaluating_codes/
│
├── datasets/
│   ├── APIs/
│   │   ├── Test_full.npz           # The original baseline API dataset
│   │   ├── malguise_full.npz       # Adversarial API dataset example
│   │   └── <technique>_full.npz    # Any other API datasets
│   │
│   └── syscalls/
│       ├── Test_syscall.npz        # The original baseline syscall dataset
│       ├── malguise_syscall.npz    # Adversarial syscall dataset example
│       └── <technique>_syscall.npz # Any other syscall datasets
│
├── mab_technique_functionality_check.py
├── ...
```

*Note: The script attempts to automatically match adversarial API sets to their corresponding syscall sets by parsing the filenames.*

## Usage and Expected Output

Navigate into the root of this directory before executing the scripts.

### 1. MAB Technique Functionality Check
Run the MAB functionality checker:
```bash
python mab_technique_functionality_check.py
```
**Output:** Generates `mab_detailed_reports.json` (per-sample similarities) and `mab_summary.json` (aggregated counts and percentages).

### 2. DQEAF Technique Checkers
Run the DQEAF integrity checker:
```bash
python dqeaf_technique_integrity_check.py
```
**Output:** Generates `dqeaf_detailed_reports.json` (per-sample alive status) and `dqeaf_summary.json`.

Run the DQEAF CFG functionality checker:
```bash
python dqeaf_technique_functionality_check.py --ori-dir Test --adv-dirs malguise gamma --report dqeaf_func_report.json
```
**Parameters**:
- `--ori-dir`: Path to the directory containing original (Test) samples.
- `--adv-dirs`: Space-separated list of directories containing adversarial samples (e.g., malguise, dqeaf).
- `--report`: The output JSON report file path.

### 3. MalGuise Functionality Check
Run the MalGuise specific evaluator:
```bash
python malguise_technique_functionality_check.py
```
**Output:** Displays a live progress bar. Upon completion, generates:
- `malguise_filtered_live_samples.json`
- `malguise_detailed_api_report.json`
- `malguise_functionality_summary.json`

### 4. Full Functionality Evaluator (Tiered)
Run the comprehensive evaluator that uses both APIs and Syscalls (BinSim Z3):
```bash
python veritas_technique_intergrity_functionality_checks.py
```
**Output:** Scans the `datasets/APIs/` directory for any adversarial `.npz` files, matches them to `datasets/syscalls/`, and runs the 3-layer evaluation. 
Generates `comprehensive_detailed_reports.json` and `comprehensive_summary.json` which includes exact Layer 2 (Z3) and Layer 3 (API) success metrics required for the research paper.

## Filtering and Combining Reports

### Functionality & Integrity Rate (FIR) Merge Script
Once you have run both the functionality and integrity scripts for a technique, you can merge their detailed JSON outputs into a consolidated FIR (Functionality Integrity Rate) report. This helps categorize samples into four strict states:
1. **BOTH**: Maintained both functionality and integrity.
2. **FUNCTIONAL_ONLY**: Maintained functionality but failed integrity (e.g. execution crashed later).
3. **INTEGRITY_ONLY**: Maintained execution integrity but the semantic functionality changed.
4. **NEITHER**: Failed both.

**Usage:**
```bash
python merge_fir_reports.py --func-report <func_report.json> --integ-report <integ_report.json> --technique <technique_name> --output <fir_combined.json>
```
*Example:*
```bash
python merge_fir_reports.py --func-report malguise_detailed_api_report.json --integ-report dqeaf_detailed_reports.json --technique malguise --output malguise_FIR.json
```

### Dataset Filtering Utilities
To ensure downstream evaluation uses only 100% correct, lived samples, you can use the provided filter scripts. These scripts take an original adversarial `.npz` dataset and a detailed report JSON, and strip out any dead or broken samples, generating a pristine `_lived.npz` dataset.

Available filter scripts:
- `filter_mab_lived_samples.py`
- `filter_dqeaf_lived_samples.py`
- `filter_veritas_lived_samples.py`

**Usage Example:**
```bash
python filter_mab_lived_samples.py --input datasets/APIs/mab_full.npz --report mab_detailed_reports.json --output datasets/APIs/mab_full_lived.npz
```
*You can also pass `--overwrite` to replace the input file directly instead of specifying an output path.*
